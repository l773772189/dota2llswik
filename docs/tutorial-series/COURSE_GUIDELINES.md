# 课程定位与编写原则（备忘录）

> **重要：** 本文件是整个教程系列的编写纲领，所有章节内容必须严格遵循以下原则。

---

## 一、课程定位

- **目标受众**：零基础小白，无编程经验，仅对 Dota 2 自定义游戏感兴趣
- **课程目标**：通过制作一个完整的 **守家类（Defense/Survival）自定义游戏**，让学员体验从零到发布的全流程
- **课程类型**：新手入门级教程，属于 Dota 2 编辑器入门系列的第一套

---

## 二、核心原则

### 原则 1：配置优先，拒绝编程教学

- **能用配置完成的，绝不写代码**
- 教程的核心是教学员通过 KV 配置文件、编辑器可视化操作来完成游戏开发
- 学员不需要学习任何编程语言，不需要理解 for 循环、if 判断等编程概念

### 原则 2：必要代码采用「复制粘贴 + 讲解用途」模式

- 当某些功能（如刷兵逻辑、波次控制）**确实无法通过纯配置实现**时，允许引入少量代码
- 引入方式：**直接提供完整代码块，让学员复制粘贴**
- 讲解方式：只说明「这段代码是干什么的」「它实现了什么功能」，**不讲解代码内部的编程逻辑**
- 例如：「把下面这段代码复制到 xxx 文件中，这段代码的作用是每隔 30 秒从出生点刷出一波敌人」
- **绝不教**：变量是什么、循环怎么写、函数怎么定义

### 原则 3：对小白友好、友好、再友好

- **每一步操作都要写清楚**，不跳步骤，不省略「显而易见」的操作
- 假设学员什么都不知道，每个按钮在哪里、每个菜单怎么打开都要说明
- 多用截图/示意图位置标注（编写时预留图片占位）
- 用通俗易懂的语言，避免专业术语，必须使用时要附带解释
- 每个步骤完成后要有「检查点」：告诉学员做完这一步后应该看到什么效果，方便自查

### 原则 4：循序渐进

- 从最简单的操作开始，逐步增加复杂度
- 每节课只讲一个知识点，不一次灌输太多
- 每节课结束都能看到一个小成果或明确的进展
- 前面的课是后面课的基础，形成清晰的学习路径

### 原则 5：操作步骤必须基于真实工具流程，严禁凭印象编写

- **所有操作步骤必须反映工具的真实操作流程和真实界面顺序**
- 严禁凭记忆、凭印象、凭推测编写操作步骤
- 启动工具后，用户第一眼看到的是什么界面？点了按钮后下一步出现什么？必须和实际完全一致
- **如果不确定某个操作的真实流程，必须标注 `<!-- ⚠️ 待验证：需实际操作确认流程 -->` ，由作者亲自在工具中验证后再填写**
- 错误示例：「打开资源浏览器 → 创建项目」（实际上要先启动编辑器看到项目列表，创建项目后才能进入资源浏览器）
- 这条原则的优先级最高——步骤写错，比步骤不写更糟糕，因为会直接让小白卡死

### 原则 6：内容要细、要详尽——禁止「压缩步骤」

- 宁可写多不可写少
- **严禁把多个子操作压缩成一个笼统的大步骤**
- 检验标准：每个步骤应该只对应学员的「一次点击」或「一次输入」。如果一个步骤背后其实包含 3 个以上的操作，就必须拆开写
- 错误示例：「编译默认地图」←这五个字背后其实是：打开 Hammer → 新建地图 → 创建地形 → 拖入预设体 → 保存 → 点运行按钮……全部被吞掉了
- 正确做法：把每个子步骤都写出来，每一步写清「点哪里、看到什么、下一步做什么」
- 如果拆完发现一节课装不下，说明这个知识点应该拆成多节课
- 操作步骤要编号，1、2、3 一步一步来
- 容易出错的地方要提前警告（⚠️ 注意事项）
- 提供「做完后的效果」描述或截图占位，让学员知道自己做对了没

### 原则 7：作者明确提到的知识点必须独立成步骤，严禁降级

- **当作者（课程负责人）在沟通中明确提到某个知识点时，说明它对学员来说是重要的，必须作为独立步骤或独立小节来呈现**
- 严禁将作者提到的知识点降级为 TODO 注释里的备注、括号里的补充说明、或一笔带过的附带提及
- 错误示例：作者说「编译和直接运行有两个按钮的区别」，结果只在 TODO 注释里写了个「这里有两个按钮」——信息被淹没了
- 正确做法：单独拆成一个步骤「认识两个运行按钮的区别」，正式讲清楚每个按钮的作用和适用场景
- **这条原则的本质**：AI 编写者不应该自行判断作者提供的信息的权重高低。作者提到 = 重要 = 必须独立呈现

## 三、课程结构与视频策略

### 每节课 = 一个知识点 = 一期视频

- **每节课时长目标：5~10 分钟**，对应一个独立的小知识点
- 每节课可以独立作为一期视频发布到抖音号/视频平台，用于引流
- 课程编号采用 `P01E01` 格式：P = Part（单元），E = Episode（节课），方便视频系列编号

### 拆分原则

- **能拆则拆**：一个知识点如果能独立讲清楚、做完能看到效果，就拆成单独一课
- **不强拆**：如果拆开后前后割裂、学员做不出完整效果，就合并在一起
- **宁可多几期短的，不要少几期长的**：3 期 5 分钟 > 1 期 15 分钟（流量角度）

### 每节课的结构模板

```
# PxxExx：课程标题（一句话说明这节课做什么）

> 一句话概括这节课的目标

## 这节课你将完成
- ✅ 具体成果 1
- ✅ 具体成果 2

## 操作步骤
（正文内容）

> ✅ **检查点**：做完后你应该看到 xxx 效果

## 下一课预告
下一课我们将……
```

## 四、代码引入的判断标准

| 情况 | 处理方式 |
|------|----------|
| 能通过编辑器操作完成 | ✅ 用编辑器操作，图文教学 |
| 能通过 KV 配置文件完成 | ✅ 用 KV 配置，说明每个字段含义 |
| 需要少量 Lua 但逻辑简单 | ⚠️ 提供完整代码，复制粘贴，讲解功能用途 |
| 需要大量 Lua 且逻辑复杂 | ❌ 重新设计功能，简化或拆分，避免出现 |

## 五、已排除的内容（及原因）

| 内容 | 排除原因 |
|------|----------|
| Lua 编程教学 | 不符合「零编程」定位，所有必要代码用复制粘贴模式 |
| 粒子特效与音效章节 | 自定义触发特效/音效需要大量 Lua（ParticleManager、EmitSound），且使用现有技能时自带音效和特效，对新手来说投入产出比低 |
| **自定义 UI 界面（Panorama）** | **Panorama 本质上是前端开发（XML + CSS + JS），属于代码而非配置。零基础小白不会写前端，即使复制粘贴也需要理解三个文件如何配合工作，复杂度远超新手承受范围。严格违反「配置优先、不碰代码」的核心原则。** |

## 六、内容编写规范

1. **每节课一个文件**：文件名格式 `PxxExx-课程标题.md`
2. **操作步骤**：使用有序列表（1. 2. 3.）
3. **代码块**：必须标注文件路径和语言类型
4. **注意事项**：使用 `> ⚠️` 引用块
5. **检查点**：使用 `> ✅` 引用块，描述预期效果
6. **图片占位**：使用 `<!-- 截图：xxx -->` 格式预留
7. **术语首次出现**：用括号附带通俗解释，如「实体（Entity，可以理解为地图上的一个物件）」
